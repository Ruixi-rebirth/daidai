# 呆呆 · 每日极客技术早报

状态：设计已落地为内置模块；当前行为以 [运行工作流](../workflow/briefing.md) 为准。当前早报整期编译为一张长图，底部为带编号和标题的文字链接索引。早期分页样张仍使用虚构资讯，仅供历史设计参考，不能作为当前输出或真实早报转发。默认每天 08:00（Asia/Singapore），订阅默认关闭，核心搭档可在目标群或私聊开启。

## 1. 最终取舍

做成呆呆内置的“每日一刊”：固定时间生成一份内容，按订阅推送到 QQ/TG；自然语言可以查看、追问、订阅或补看。复用现有 API Provider、Typst 编译器、通信通道和引用缓存，不另做 CLI、crontab、TG 客户端、Webhook、消息总线或通用任务平台。

每日的产品目标是三分钟读完、有原文可点、可以接着聊。五个栏目为 HN 精选、AI 研究精选、GitHub 开源发现、V2EX 技术话题、NixOS 生态；NixOS 排最后。AI 栏目使用 Hugging Face Daily Papers 官方 API，只选过去 24 小时内进入日选、带有论文摘要的研究，不把社区投票当成论文结论的验证。模型厂商的产品发布不再各自增加一个来源，仍由现有 HN 和 GitHub 候选覆盖。每个栏目目标五条，各最多五条，整期上限 25 条；不足时少发，不用旧资讯补足，也不输出空栏目凑版面。

建议默认每天 08:00（Asia/Singapore）开始生成，通常随后几分钟送达，不能把“08:00 开始”承诺成“08:00 整一定收到”。支持核心搭档私聊及明确开启订阅的群；群友只读查看，搭档管理订阅。默认渠道建议 TG，QQ 可另行开启；没有明确订阅前不自动向任何渠道广播。

本轮对初稿的重要修正：

| 初稿的不足 | 收敛后的决定 |
| --- | --- |
| 按热度先选好 12 条，再让模型翻译 | 代码过滤、去重并提供最多 44 个候选，一次模型调用同时选题和编辑，给低热度重要公告留机会 |
| 论坛首帖摘要可能写成讨论共识 | 输入标明实际读到的材料；未读评论时只概括首帖问题，不评价“大家认为” |
| 单张长图比例过于细长 | 专用单列报刊模板，正文 16pt、画布 860pt，增加每行信息量以减少换行；保持一张整图，缩略图显示尺寸由客户端决定 |
| 逐分片回执系统与现有发送层重复 | 每期、每接收者一条投递记录，复用通道的成功/部分送达语义，不另造发送引擎 |
| 订阅放平台状态、刊物放另一库 | 共享库三张业务表：刊物、订阅、投递；授权仍由原身份系统管理 |
| 声称现有通道已全部支持逐页语义 | 本次已补齐 QQ 逐图来源与部分交付语义，和 TG 共用语义恢复计算 |

## 2. 日常使用

| 用户说的话 | 行为 |
| --- | --- |
| 今天的极客早报 | 返回今天已发布的版本；未发布时说明状态，不悄悄重做昨天的内容 |
| 现在生成一份今天的早报 | 没有已发布版本时生成；已有版本直接使用，不重复扣模型额度 |
| 第三条展开讲讲 | 根据当前引用/最近展示的刊物，找到全期 03 号的资料；必要时调用现有 read_link 深读 |
| 昨天第三条原文 | 按刊物日期和条目号返回已归档链接，不依赖聊天记录尚未被 /reset 清理 |
| 以后每天把早报发到这里 | 由核心搭档在当前群或私聊开启该会话订阅，回执写清时间、时区、渠道 |
| 关闭这里的早报 | 仅关闭当前平台，另一个平台不受影响 |
| 早报现在订阅到哪里了 | 展示当前订阅、生成时间、最近一期投递状态 |
| 继续早报 / 补发今天的早报 | 有明确未送达正文时只补剩余部分；已经送达时不自动重发整份 |
| 把今天早报完整再发一次 | 明确的重发请求，可再次交付已有刊物，不重新抓取或总结 |

“第三条”始终指全期 03 号，不是当前图片里的第三个标题。存在引用时以引用刊物为先；没有引用时使用该会话最近展示的刊物；均无法确定时再询问，不从其他会话猜。最近展示的刊物引用按平台、会话、用户隔离并持久化，不能只存在进程内。

管理限核心搭档，可在当前群或私聊执行；已开启订阅的群内允许群友只读查看和追问。没有订阅的其他群及访客私聊不开放，不新增 slash 命令。工具层再次检查权限，不能只靠提示词。工程落地可用一个查询工具和一个管理工具，保持“查询已有内容”与“生成/订阅/重发”等写操作的权限边界清楚。

提前明确要求生成的版本可成为当天正式刊物；当天定时任务发送这份内容，不再自动重做。早于发送时间的普通“看看今天早报”不会被解释为提前生成。

## 3. 采集与时间语义

### 来源

| 栏目 | 入口与材料 | 选择边界 |
| --- | --- | --- |
| NixOS | 官方 RSS `https://nixos.org/blog/announcements-rss.xml`；Discourse 公告 `/c/announcements/8.json`、开发 `/c/dev/14.json`、教程 `/c/howto/15.json`；主题首帖 `/t/{id}.json` | 不读取全站热门或求助区。开发和教程仅取 24 小时新主题，旧公告必须读到 24 小时内新内容。允许新置顶公告，排除开发/教程置顶说明及旧 PR 催审队列。官方公告、社区公告、开发与教程分别标注；话题链接为 `/t/{slug}/{id}`。 |
| HN | `https://hacker-news.firebaseio.com/v0/topstories.json` 的前 60 个 ID，再请求 `/v0/item/{id}.json`；入围文章补正文摘录或页面摘要 | 保留有效 story，过滤 deleted/dead/job。score 用于排序，150 分是优先参考，不是硬门槛。没有读评论就不生成评论共识。保留原文和 HN 讨论两个入口。 |
| GitHub | `https://api.github.com/search/repositories`；入围仓库使用描述和有限 README 摘录 | 两路：近三天创建的新项目、近期维护的 NixOS 项目。显式限定公开、非归档、非 fork。总 Star 不是今日涨幅，pushed 不等于重大更新；显示“新项目/近期维护”，不声称是日增榜。 |
| V2EX | `https://www.v2ex.com/api/topics/hot.json`，候选不足时取一次 latest；主要材料是主题正文 | 按实际创建时间过滤，提供技术相关候选；默认排除交易推广和无关生活内容。只读首帖时，摘要描述发帖者的问题或经验，不能用回复数推断讨论结论。 |

GitHub 查询参数用 `url.Values` 构造。新项目示例：`created:>=<三天前时间> stars:>50 is:public archived:false fork:false`；NixOS 示例：`topic:nixos pushed:>=<一天前时间> is:public archived:false fork:false`。两个请求各取有限结果，按仓库 ID 合并。API 返回 incomplete_results 时记录来源不完整，不能称“完整排行榜”。

旧 NixOS 主题最多额外取末尾三个帖子 ID 对应的回复（`/t/{id}/posts.json?post_ids[]=...`），只保留窗口内有可读新内容的候选，并把新回复与首帖分开作为证据。取不到新回复就跳过旧帖，不递归读完整讨论，不把“再次活跃”当成发布。接口用法依据 Discourse 官方客户端，已在目标站的公开主题上实测匿名取得三条指定回复及各自时间；不假设所有主题都可匿名读取。

上述入口已在 2026-11-16 实测：NixOS RSS 可读取；Discourse 公告类别 ID 为 8、主题 JSON 有首帖 cooked；HN topstories 返回 ID 列表；GitHub 搜索返回 created_at/pushed_at/总 Star；V2EX hot 包含主题正文及回复数。此证据证明接口和材料可用，不代表未来永远可用，也不代表已完成生产抓取器。

### 窗口与去重

以本轮候选采集结束时刻作为 `cutoff`，统一筛选 `[cutoff-24h, cutoff]` 的新资讯；每个来源另外记录 observed_at。热度数字是各源实际抓取时的快照，不假装是精确的 08:00 历史统计。GitHub 新项目例外使用 72 小时发现窗口，必须有相应标签。

这是有限候选中的精选，不是对过去 24 小时所有消息的穷尽检索。重试时尚未发布可以重新采集；一旦发布，cutoff、条目号、内容与原链接冻结，两个平台共享同一期。发送失败不重新采集。

来源状态分为正常、有部分数据、没有合格内容、获取失败。部分数据可继续参与编辑，并在刊物中用一行注明缺失来源；抓取正常但没有新内容不是故障。全部来源获取失败时标记当日生成失败，窗口内有限重试，不调用模型、不发送“今天没有新闻”的假空刊。只有成功获取资料后确实没有合格内容，或有效编辑结果为空，才能发布空刊。

跨站相同原文、同一仓库合并，保留多个讨论入口。以原生 ID、仓库 ID 和明确的规范链接去重，不做标题正则或模糊字符串拼接。URL 只去掉已知追踪参数与片段，保留可能改变内容的参数。

最近七天出现过的同一原文/仓库默认不再推荐。首版不因总 Star 或 pushed_at 变化就重新收录；明确的新版本公告可按新的发布 URL 独立进入候选。去重历史来自已发布刊物；只抓过但未发布的材料不算“已经推荐”。

## 4. 选题与编辑：一次模型调用

处理顺序固定为：采集 → 时间过滤/跨站合并/历史去重 → 有限候选与补料 → 一次编辑 → 校验与条目定稿 → 归档 → 渲染和投递。通过字段长度与条目数量上限约束版面，条目取舍和编号分配均在归档前完成；渲染失败时交付完整同源文字，不在发布后悄悄删除条目。

代码只做可确定的过滤，不堆一套关键词打分来假装判断技术价值。编辑前按来源限流：NixOS、HN、GitHub、V2EX 各最多 8 条，AI 研究最多 12 条；合并重复后最多 44 条，再受总输入 40,000 字符上限约束。官方新公告优先保留。各源自己的热度只用于缩小候选，不跨站比较 Star 与分数。

编辑模型在这些材料里选择最多 25 条，五个栏目各最多五条，给出栏目内顺序和最多两条头条引用。上限是防止某个来源淹没整期，不是要每栏填满。论文实验结论必须标为作者报告；单一来源的安全、隐私或漏洞主张需要归属来源，并保留明确的影响范围和前置条件。固定编辑兴趣为 NixOS/Linux、自托管、开发工具、开源基础设施及有实际技术内容的 AI；不读取用户私聊、个人记忆或宿主配置来“个性化”新闻。

输入每条提供：不透明候选 ID、来源 ID、标题、时间、指标、原文/讨论 URL、正文摘录和 evidence_kind。取材优先级：源站结构化正文 → 可可靠提取的正文片段/页面摘要 → 只有标题。HTML 使用项目已有解析依赖处理，不用正则剥标签，不执行页面脚本。只补候选材料，不启动 Chromium，不逐条调用 AGY。页面不可读就降级，用户想深入时再使用现有网页工具。

模型输出结构化 JSON，例如：

```json
{
  "items": [
    {"id": "hn:123", "title_zh": "中文标题", "summary_zh": "基于已提供材料的摘要。"}
  ],
  "lead_ids": ["hn:123"]
}
```

输出顺序表示编辑选择；栏目、指标、链接、证据等级由程序从候选映射，模型无权改写。定稿后按栏目赋予全期 01…12 编号，头条 ID 同步映射；页码不参与条目编号。

标题目标 30 字，上限 60 字以保留完整项目名；摘要目标 45–80 字、最多两句，上限 120 字。超过摘要上限时只保留边界内的完整句子，没有合适短句时只保留标题，不硬切半句。作者主张使用“作者提出/发帖者认为”等归属表达，不把观点写成已经验证的事实。

**只有标题时只能做标题速览，不能强行补两句价值分析。** 对 title_only 条目，代码忽略模型生成的摘要并强制显示标题速览，不只依赖提示词自律。读到 README 不等于验证过项目，读到文章摘录不等于读过全文。材料类型必须贯穿到生成规则和展示标记。结构与 ID 校验只能防止格式和链接错误，不能证明所有摘要在语义上都正确；验收必须人工核对一批真实样本。

默认一次只读 API 编辑调用，复用现有 Provider，不切换聊天首选模型，不开放工具，不额外调用“是否出图”或“修复 JSON”的模型。这里的一次指生成早报的编辑阶段；用户正常聊天理解和后续深读仍走现有对话流程。

未知 ID、重复或超出栏目额度时过滤该条，保留其余有效条目；JSON 结构完全不可用或没有有效条目时才整体回退基础速览。模型明确返回无值得推荐内容且输出有效时，接受空刊，不补足低价值候选。回退不再调用另一个模型，明确显示“本期为基础速览”。

整份基础速览控制在六条以内，优先使用已有正文或描述的材料；没有经过模型选题时不冒称“今日最值得关注”。这种情况宁可更短，不把全部候选倾倒给用户。

## 5. 呈现：先适合手机阅读

早期分页样张为 `geek-briefing-preview.png`、`geek-briefing-preview-2.png`、`geek-briefing-preview-3.png`。源数据为 JSON，Typst 模板为 .typ；所有样张均为虚构条目。

- 当前单列 860pt 画布（导出宽度 1720px），正文 16pt、条目标题 20pt、次要信息 12pt，中文使用思源黑体，英文编号使用等宽字体，图标沿用 Twitter Emoji。采用紧凑条目与更高的信息密度，通过减少换行、内边距和条目留白降低整图的长宽比；不能将导出宽度等同于聊天窗口的缩略图宽度。
- 白底、深色正文；栏目使用少量不同强调色。日期与统计截止时间明确，元信息弱化但保持可读对比，不给每个普通标题都套大蓝色标题。
- 顶部只用两条短标题做“先看这两条”，编号与正文对应。正文每条只讲一次，不为头条再复制整段摘要。
- 每期最多二十条，按栏目连续排成一张完整长图。高度随内容增长，保持字号、不截断条目；图片编译验证大小与像素上限，失败则交付同源文字。
- 整图原文与最终刊物一致；链接目录只覆盖最终收录条目。TG 照片规格不允许的长图以完整图片文件发送。

同一 JSON 产生三种视图：图卡、含链接的精简索引、文字回退。三种视图不各写一套内容，模型也不再分别生成三遍。图卡使用常量 Typst 模板读取有界 JSON，把外部标题和摘要当作普通字符串，不把网页文字拼接成可执行 Typst 代码。

图片里的链接不能点击。TG 优先整期长图＋一条带标题的链接索引，索引使用现有链接实体，避免完整 URL 撑满窗口。QQ 采用已有能力：能用多图 Markdown 合并则合并，不能则按实际平台限额交付；链接受平台限制时给出平台允许的原文入口，不绕过限制或引入短链。首版不添加按钮系统或托管网页。

索引例：`03 · 资讯标题`，HN 可另附“讨论”。不重复摘要，不追加“见图/随图长图/以上是今日早报”。不能把跨平台消息形态承诺成“总是一条消息”。

## 6. 先补齐引用语义，再上线

当前代码证据：

| 能力 | 当前状态 | 上线要求 |
| --- | --- | --- |
| TG 逐图语义 | transmit.go 已按 ImageSources 保存每张图的正文与对应消息 ID | 当前早报只有一张图，传整期正文 |
| QQ 普通多图 | 本次已消费逐图 ImageSources，媒体发送保留 text_card 类型 | 当前早报传整期正文；多图通用发送仍按真实送达语义保存 |
| QQ 多图 Markdown | 多页可以属于同一平台消息 | 被引用的是整条图文消息时恢复整期；不能凭空断定用户点的是其中第几张图 |
| 现有分页 | Cortex.RenderCardPages 基于字符数切分、最多四页 | 早报使用结构化条目整期长图，复用 Typst 编译和图片验证，不复制进程执行器 |
| 延迟通知 | pending_notifications 目前只有文字 body | 不把它当作已经具备图片投递和逐片恢复能力的通用队列 |
| 通道发送返回值 | Channel.Transmit 返回 error，没有通用消息回执列表 | 投递表不假设能取得每个消息 ID；逐消息引用索引仍由适配器维护 |

归档内容中包含刊物日期、全期编号、原文 URL、证据摘录和最终摘要。已发布刊物不再重排条目；重渲染可改善视觉样式，整图原文写入平台引用缓存，重启后能直接还原自己的渲染图，不再 OCR。原文首行保留刊物日期，因此即使脱离最近会话，也能查询正确一期。早期归档中的分页字段不参与当前呈现，内容和编号保持不变。

没有引用且只说“第三条”时，使用最近一次成功向该会话展示的 edition_id；在订阅记录中保存该值。查询旧刊也更新展示上下文。/reset 清除对话指代上下文时一并清除这个指针，早报归档本身仍保留。

实际送达的正文才写入对应平台聊天历史。主动推送不能伪造一条用户消息来调用 Memory.Commit，否则可能触发用户事实提炼或错误回复归属；使用明确的机器人出站记录入口。部分成功只记录已知成功的正文，不把失败页写成已发。新闻永远不作为用户个人事实。

## 7. 日期、重启与并发

一天一个正式版本，唯一键为刊物本地日期；记录生成时使用的时区和 cutoff。发布日期确认后不覆盖正文。修改全局时区/发送时间只影响未来自动调度，不悄悄重做已有日期。

| 场景 | 规则 |
| --- | --- |
| 定时开始生成，同时用户索要 | 合并同一期在途操作，用户可等待或获得生成中状态，不并发两次采集 |
| 今天已发布，再次查看 | 只读归档；重新发送与重新生成分开 |
| 重启发现未完成生成 | 旧任务标记中断；窗口内允许重新尝试，没有发布过才能重做 |
| 重启发现发送中 | 记录为结果不确定，不能当作“没发送”全量重发 |
| 08:00–10:00 内启动 | 生成尚未发布的今日版本，并投递未完成订阅 |
| 10:00 后启动 | 不自动刷迟到早报；可通过明确手动请求生成，标注实际截止时间 |
| 多天没开机 | 不补发多天历史早报 |
| 早于 08:00 明确提前生成 | 成为当日正式版本；08:00 使用该刊，不重复编辑 |
| 模型失败但素材可用 | 发布基础速览，也是当日版本；不会每次查看又重试模型 |
| 有效空刊 | 一条简短文字说明“本期没有筛选到值得推荐的新内容”；归档为空刊，不发四张空图 |

定时器只负责唤醒同一服务函数，使用 IANA 时区计算下一次本地时间，不拿固定 24 小时替代日历。生成与发送分开：同一期只编辑一次，两个平台各自投递；一个平台失败不让另一个平台重发。

根服务停机取消全部操作。并发等待者取消只停止自己的等待，不启动替代任务；实际生成任务由其发起上下文/服务生命周期取消。取消后由明确的新调用或调度重试接管，不自动递归重跑。所有状态变化短事务完成，不持有数据库事务等待网络或模型。

## 8. 存储：三个实体足够

使用共享 `data/db/briefing.db`，通过同一个 SQLite 驱动和受保护的连接初始化管理。应抽取现有通用连接初始化供复用，而不是把 briefing 当成假平台调用 GetConn，从而生成一套无用的 messages/user_roles 表。没有跨平台库复制同一期的操作。

| 表 | 主要字段与约束 | 用途 |
| --- | --- | --- |
| brief_editions | id/本地日期唯一，timezone、cutoff、status、content_json、model_id、created_at/updated_at、error_kind | 保存一期不可变的结构化内容、各源状态和必要证据；status 为 generating/ready/empty/failed |
| brief_subscriptions | (platform, recipient_id, is_group) 唯一，owner_key、enabled、last_viewed_edition_id、updated_at | 群或私聊订阅和当前指代上下文；关闭订阅用 enabled，不删除历史身份记录。查看但未订阅时也可存在 disabled 记录 |
| brief_deliveries | (edition_id, platform, recipient_id, is_group) 唯一，status、attempts、next_attempt_at、delivered_text、remaining_text、last_error_kind、notified_at、updated_at | 每接收者每期一行，保存投递及补看进度，关联刊物与接收者 |

订阅只存偏好与地址，不能改变角色。查询入口的安全校验仍由身份模块完成。edition_id 和原生来源 ID 不靠标题拼接；外键、状态 CHECK、布尔 CHECK、唯一键与短事务维护一致性。完整资料 JSON 在写入层校验合法性与大小，常用日期/状态/重试时间用列和索引，不用 JSON 全表扫描驱动调度。

保留已发布历史刊物和投递状态；只保留入选条目的必要摘录，不存整站 HTML、所有评论或所有候选。图片仅作可删除缓存，可用归档重渲染。既不为功能上线清空数据库，也不引入迁移中间态设计。

## 9. 投递与失败处理

继续通过 ChannelRegistry.Transmit 发 Utterance，正常内容优先合并多图。正式发送前准备好整期版式，避免先发一半才发现后面渲染失败。渲染失败时整期退回同源文字格式，原文索引仍保留；发送已开始后不盲目从头换格式重发。

投递状态明确区分：pending → sending → sent；另有 retryable、partial、uncertain、expired。每行保存下一次尝试时间，进程重启也遵守冷却；自动重试最多三次、间隔至少五分钟，仅在当日窗口内发生。

| 结果 | 后续行为 |
| --- | --- |
| 渲染/本地校验失败，尚未发任何消息 | 可以安全降级或稍后重试，不标成已投递 |
| 平台明确未接收且可重试，例如可信限流拒绝 | 遵守 Retry-After 与窗口，有限重试 |
| 平台明确永久拒绝，例如权限关闭 | 不持续重试；保留已生成刊物及失败状态 |
| 已知部分送达 | 通过现有 PartialDeliveryError 保存已送/剩余正文；补看默认只交付剩余文字，不重新发送已成功图片 |
| 超时、连接在提交后断开、回执无法确认 | 标成 uncertain，不自动全量再发；保留内容，待用户明确补发 |
| 错过当天自动窗口 | pending/retryable 标记 expired；partial/uncertain 保留原状态但停止自动尝试，手动仍可查看已有刊物 |

“是否可能已投递”由适配器依据请求阶段与结构化平台响应提供，不在业务层匹配错误字符串。已补齐 UnsentError（消息未尝试发送）与 DeliveryRejection（平台明确拒绝）；未知错误默认 uncertain。不能仅凭 HTTP 5xx 就保证平台没接收，也不能用本地唯一键声称端到端 exactly-once。

QQ/TG 已共用 ImageDeliveryText 计算已送与剩余语义，QQ 保留逐图 source。没有新造逐 HTTP 分片回执协议；如果平台回执不足以确认某部分，保守保存为不确定并保留整期供用户补看。

失败不会无声丢弃。核心搭档下次私聊时可用一条简短状态提醒告知最近一期未完整送达，同一异常只提醒一次，正常回复优先保留额度。过期整刊不会在用户回来时连发多份；用户也能通过自然语言查询失败原因和补看。现有 pending_notifications 不再存第二份早报正文，避免两个队列分别重发。

## 10. 接收者、配置和资源

TG 订阅地址只来自核心搭档通过当前 owner_username 校验后明确操作的当前群或私聊事件。数字 chat_id 是路由地址，不是新增的 ID 授权配置；不能用普通用户的 @username 直接反查私聊 chat_id。订阅时登记地址与当时校验的用户名，发送前用 getChat 取该私聊当前信息，再按当前配置的用户名不区分大小写核验；无匹配用户名、信息不完整或核验失败时本次不发送，等待重新验证的私聊。群和话题订阅保留完整路由，getChat 核验实际群 ID 及群类型；群与私聊使用不同订阅和投递键。

QQ 以当前配置搭档 OpenID 核验。修改 owner 配置或关闭订阅后，旧地址不能继续靠历史订阅获得发送权限；关闭订阅取消在途投递并禁止后续请求，但已经被平台接受的消息无法撤回。所有平台仍受各自主动发送权限约束，不能保证 QQ 主动发送必定成功。

非敏感静态配置仍走 YAML/Nix：enabled、timezone、time；模型和可选 GitHub Token 走现有秘密管理。订阅开关与地址只以数据库为准，首次启用由自然语言登记，不在配置文件和数据库同时维护两份接收者名单。首版全局一个生成时间，不引入每用户 cron 表达式或多个不同截止版本。

建议资源预算是实现上限，不是已经测得的性能保证：

| 阶段 | 预算 |
| --- | --- |
| 采集候选和补料 | 整体 60 秒，单个 HTTP 最多 8–12 秒，全局并发最多 6；同一来源最多占 3 个，防止 HN 详情挤占其他源 |
| 原始抓取 | 每个响应解压后限制 2 MiB；只读必要数量，不跟随无限分页 |
| 编辑材料 | 最多 44 个候选，每条摘录最多 1,400 字符，含元数据总输入最多 40,000 字符 |
| 模型编辑 | 一轮，最多 90 秒，输出最多约 6,000 tokens，并受响应体大小限制 |
| 最终排版 | 上限 25 条、一张完整长图；复用每图 10 MiB/20M 像素检查，缓存不得无限累积 |
| 生成总体 | 最多 3 分钟，受停机和主动取消约束；投递另有独立超时，不占住生成锁 |

受限共享额度不足时，优先保留元数据、官方公告和少量完整材料，不扩大并发或盲目放宽超时。任务与普通聊天争用资源时，早报不得占住会话锁；模型调用与渲染限并发，实际 1GB 环境须测峰值，包含 Typst 子进程 RSS，不能只看 Go Heap。未实测前不承诺“额外内存固定低于某数值”。

外部抓取使用现有受保护 HTTP 客户端，校验每次跳转、解压后大小和 URL；外站请求不携带模型/GitHub 凭证。HTML 和 Markdown 均为不可信数据，外链不允许直接形成任意文件读取或 Typst 源码。日志只记录来源、计数、耗时和错误类别，不打印密钥或大段网页正文。

## 11. 落地边界

新增 internal/briefing，职责可以用 source_nix/source_hn/source_ai/source_github/source_v2ex、service、editor、store、delivery、scheduler 几个普通文件表达。五个来源用函数列表即可，不提前建设插件系统。render 包加入结构化早报模板并复用已有编译器、字体和图片检查；通道只补齐语义和错误分类，不在早报模块直接调用 Bot API。

推荐实现顺序：

1. 采集与编辑，落盘一份有依据的结构化刊物；先看真实内容质量。
2. 专用图卡、索引、引用与追问，补齐 QQ 的逐图语义并完成真实客户端验证。
3. 订阅、调度与投递状态，覆盖失败恢复，再启用自动推送。

以上是实现顺序，不是把后两项留作“以后再说”。只有生成、阅读、追问和投递一起验收通过，才称功能上线完成。首版不包含 Web 页面、按钮交互、全站趋势数据库、用户画像推荐系统或替其他会话远程订阅。

## 12. 验收清单

- 内容：逐条核对真实样本的标题、摘要、正文依据、指标与原链接；测试“只有标题”“只读首帖”“观点归属”“空刊”“模型失败”不会伪造信息。结构校验通过不等于内容正确。
- 时间：24 小时和 72 小时边界、来源 observed_at、提前生成、窗口外启动、跨天重启、时区变化、旧主题活跃不冒充新发布。
- 筛选：置顶说明页、广告交易、已推荐原文、同仓库跨站出现、发布失败不计入七天去重；栏目不足不强行填满。
- 模型：默认一次编辑调用，坏 JSON/未知 ID/超长摘要安全回退，不暗中加一轮修复，不把图卡选择再交给模型。
- UI：390px 左右屏幕宽度下正文可读，真实最长标题和 CJK/英文混排不溢出；用 8、12、25 条及单条长内容验证整图完整性、条目边界和标题索引一致。
- 引用：分别引用 TG 相册单页、QQ 单独图片、QQ 合并图文；确认页与整期语义区别、重启后的原文恢复，以及“昨天第三条”和 /reset 后的指代边界。
- 投递：同日并发生成只一次；两个平台失败互不影响；在 sending 阶段崩溃后不全量重发；部分成功、429、明确拒绝、结果不确定和过期逐项覆盖。
- 身份：TG 改用户名、owner 配置变化、关闭订阅、无权限私聊、未订阅群和群中管理请求不能绕过边界；地址不能替代身份。
- 性能：真实小内存机器测包括 Typst 子进程的峰值与并发聊天延迟；来源超大响应、慢响应、坏格式、跳转及全体失败均有界退出。
- 运行：状态查询能看到最近刊物、订阅、投递结果和下一次时间；未投递内容不伪造已送历史，新闻不进入用户个人事实。

这些是实现后的上线门槛，本轮设计并未声称已通过生产验收。

实现补充：入模投影只保留编辑必要字段，总量超限时统一缩短摘录，避免某一个栏目整体被挤出；原始证据仍保留在归档。实际行为和已验证边界见运行工作流。

## 13. 本轮设计核验

- 核对现有 QQ/TG 的 Transmit、逐图引用、部分送达、通用通知及数据库初始化代码，将不能直接复用的能力列为第 6/9 节的实现前置项；没有仅凭接口名称推断能力。
- 通过真实只读 HTTP 请求验证四类来源入口与所需字段，并验证 Discourse 旧主题可匿名读取指定末尾三条回复。没有发送 QQ/TG 测试消息、变更订阅或使用真实早报假装样张。
- 三页样张由同一份 JSON 和 Typst 模板实际编译；9 条编号无重复、头条引用有效、标题速览没有伪造摘要，原文索引从同一 JSON 生成。
- 利用 Typst 布局元数据核对 01–09 的实际页与计划页一致。三页 PNG 分别为 880×1393、880×1246、880×1140。
- 另用 12 条、每条 30 字标题/80 字摘要/40 字元信息的极限样本实际编译为四页，12 条均位于计划页。最大一页为 880×1769，均未超过现有像素限制。这证明样板版式具备容量，不代表自动分页算法已经实现。
- 在约 390px 宽显示时，440pt 画布上的 18pt 正文字号约相当于 16px；已检查三张图的字体、Emoji、分区、续栏与页码。真实 QQ/TG 缩略图、压缩和点击体验仍列入上线验收。

重建样张：在仓库根目录运行 `nix develop --command typst compile docs/design/geek-briefing-preview.typ 'docs/design/geek-briefing-preview-{p}.png'`；输出的第 1 页对应文档中的 `geek-briefing-preview.png`。源 JSON 的示例 URL 使用 example.com，链接样张仅展示入口形态，不是生产链接。
