## 已确认并修复

1. `/stop <工单编号>` 在命令注册表中可以执行，但队列只让无参数 `/stop` 走即时控制通道。有参数的中断可能等待普通对话结束。现在两种形式都走即时控制通道并共享独立的停止事件容量；不会误匹配 `/stopping`。
2. Telegram 停机只调用队列 `Stop`，未等待已经开始的处理完成，主进程可能继续关闭记忆及数据库。现在复用现有 `Shutdown(ctx)` 等待处理协程，超时会返回错误；调用者可以重试等待，避免另造一套生命周期逻辑。

## 第二批：引用与附件边界

3. Telegram 原本先将整条引用链的文件追加到当前事件，再将该事件保存为引用记录、登记为当前发言者的待处理附件。连续引用会把祖先附件复制到每一层，并让他人的文件成为自己的待处理上传。改为先保存消息本身及引用链，处理时才去重展开引用文件；待处理列表只登记本轮实际上传附件。回归检查覆盖三次连续引用以及跨用户待处理列表隔离。
4. Cortex 为模型整理引用正文时会执行单条和总预算截断，但沿用原来的完整状态。改为在任一截断后标记正文不完整，完整正文仍保持完整；回归检查覆盖单条超限与总预算不足。

本批 Telegram、chat 的普通与 race 测试通过。已读取 CLI 工作者的目录校验、进程组取消和输出处理，以及工单队列注册、容量与工作区租约路径；模型路由只完成部分阅读，尚不能认定审查完毕。
