## 已确认并修复

1. `/stop <工单编号>` 在命令注册表中可以执行，但队列只让无参数 `/stop` 走即时控制通道。有参数的中断可能等待普通对话结束。现在两种形式都走即时控制通道并共享独立的停止事件容量；不会误匹配 `/stopping`。
2. Telegram 停机只调用队列 `Stop`，未等待已经开始的处理完成，主进程可能继续关闭记忆及数据库。现在复用现有 `Shutdown(ctx)` 等待处理协程，超时会返回错误；调用者可以重试等待，避免另造一套生命周期逻辑。

## 第二批：引用与附件边界

3. Telegram 原本先将整条引用链的文件追加到当前事件，再将该事件保存为引用记录、登记为当前发言者的待处理附件。连续引用会把祖先附件复制到每一层，并让他人的文件成为自己的待处理上传。改为先保存消息本身及引用链，处理时才去重展开引用文件；待处理列表只登记本轮实际上传附件。回归检查覆盖三次连续引用以及跨用户待处理列表隔离。
4. Cortex 为模型整理引用正文时会执行单条和总预算截断，但沿用原来的完整状态。改为在任一截断后标记正文不完整，完整正文仍保持完整；回归检查覆盖单条超限与总预算不足。

本批 Telegram、chat 的普通与 race 测试通过。已读取 CLI 工作者的目录校验、进程组取消和输出处理，以及工单队列注册、容量与工作区租约路径；模型路由只完成部分阅读，尚不能认定审查完毕。

## 第三批：部分投递的语义恢复

5. Telegram 只记录部分投递中的短文字，未计入文字卡片正文。现在依据已确认的图片批次整理完整送达与待续发的正文；同一正文对应多页时，只有全部相关分页成功才视为正文完整送达。未完成正文去重保留，可通过现有文字续发机制补看；未发送的真实图片明确提示无法靠文字补回。异常相册回执仍保持部分投递语义，避免退化为整条自动重发。

覆盖场景：11 页卡片的最后一页失败、卡片成功但后续文字失败、真实图片与文字卡片混合。Telegram 测试及 race 检查通过。

进一步检查了调度器的签发快照、工作区冲突、执行超时、取消后容量释放、终态持久化与模型输出摘要，以及模型池刷新版本控制、状态保存失败回滚和 CLI 工作者输出。AGY 会话门控已核对 defer 释放顺序；尚需继续检查完整执行/认证路径与其余工具、数据库、记忆。

## 审查原则（用户明确要求）

- 修改前先审视功能设计与数据归属，比较更简单、效果更好的方案；结构有问题时允许重构，不以保留旧实现或缩小 diff 为目标。
- 避免用重复状态、补偿分支和字符串拼接掩盖职责问题；新增字段或辅助函数必须有明确且不可由现有状态可靠替代的语义。
- 前三批修改也纳入回看，最终验证必须覆盖正常聊天、失败恢复和权限边界。

## 第四批：历史上下文边界（进行中）

6. 当前消息先入库、后取最近历史，会使本轮请求在历史和当前输入中重复出现；处理积压消息时也会看到后来入库的排队消息。采用按消息记录 ID 的单一历史边界，在数据库限量查询前排除本轮及后续消息，合并请求保留最早入站记录作为边界，最后一条记录继续用于消息归属与摘要更新。近期上下文和跨场次摘要共用同一边界，避免读取后再过滤导致真正历史被 LIMIT 挤掉。SQL 同时合并了原本按时间/按 ID 重置边界的重复查询模板。

覆盖单消息、合并请求、20 条排队消息挤占 LIMIT、重置边界；db、memory、kernel、chat、Telegram 测试及 db/memory/kernel race 检查通过。

权限目标解析另发现两项待处理问题：名单查询错误被忽略、同名昵称直接选择第一个目标。接下来应让目标解析在资料缺失或同名歧义时明确失败，并优先匹配真实 OpenID，减少误授权机会。

## 第五批：权限目标解析重构

7. 权限目标解析此前忽略数据库错误，并在多个分支中重复构造目标；序号越界可能落到另一份名单，同名昵称也会直接选中第一人。现在先读取权威名单，读取失败即停止；转为统一目标结构后，由纯函数执行完整 OpenID 优先、明确名单序号与唯一昵称解析。减少了重复分支，未引入额外持久状态或解析正则。新增检查覆盖跨名单同名、显示名冒充 OpenID、序号越界、明确指代和数据库读取失败。
8. `grant friend` 对已有协作者实际保留协作者权限，但旧回执错误声称仅有好友权限。授权 SQL 直接 `RETURNING role` 返回本事务的最终角色，内存同步与回执使用该结果，明确降级仍走 `modify`；不新增一次外部回查或推测角色。
